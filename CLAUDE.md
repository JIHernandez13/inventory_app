# CLAUDE.md - AI Assistant Guidelines for inventory_app

## Project Overview

**inventory_app** is a Flutter (Dart) mobile app for tracking groceries, home
goods, appliances, and tools, with a fully on-device database (no cloud sync
in v1) and a swappable "inventory scheme" presentation layer — the flagship
scheme is a Legend of Zelda-inspired inventory grid, with room to add more
game-inspired schemes later.

- **Language**: Dart
- **Framework**: Flutter (targets: Android, iOS; Linux desktop is also
  enabled purely as a convenient local dev/test target, it is not a shipping
  target)
- **State management**: Riverpod (`flutter_riverpod`)
- **Local database**: `drift` (SQLite-based, reactive queries, real
  migrations)
- **License**: GPL v3
- **Status**: Early development

## Build & Dev Commands

```bash
# Install dependencies
flutter pub get

# Run the app (pick a connected device/emulator, or -d linux/-d chrome for desktop/web dev)
flutter run

# Regenerate drift/build_runner generated code after changing tables or annotations
dart run build_runner build --delete-conflicting-outputs

# Static analysis (must be clean before committing)
flutter analyze

# Format code (must be applied before committing)
dart format .

# Check formatting without writing changes (what CI runs)
dart format --output=none --set-exit-if-changed .

# Run all tests
flutter test

# Run a single test file
flutter test test/path/to/some_test.dart

# Build a release Android APK / iOS app
flutter build apk --release
flutter build ios --release
```

## Development Workflow

### Before Committing

1. Run `dart format .` to format code
2. Run `flutter analyze` and resolve all warnings/errors
3. Run `flutter test` and ensure everything passes
4. If you changed drift tables/DAOs or any `@riverpod`/build_runner-annotated
   code, re-run `dart run build_runner build --delete-conflicting-outputs`
   and commit the result only if the project has decided to check generated
   code in (see `.gitignore` — by default `**/*.g.dart` is NOT committed;
   CI regenerates it)
5. Run `gitlint` (or rely on the `commit-msg` hook) to check your commit message

### Issue Tracking & Release Notes

- The build is tracked as phases under the roadmap issue
  [#4](https://github.com/JIHernandez13/inventory_app/issues/4), one
  sub-issue per phase. Each phase's PR should reference/close its issue
  (e.g. `Closes #6`).
- [`CHANGELOG.md`](../CHANGELOG.md) records what shipped in each phase
  (Keep a Changelog format). Add an `### Added`/`### Changed`/`### Fixed`
  entry under `## [Unreleased]` as part of the PR for a phase; when a
  phase's PR merges, that becomes its dated release entry.
- **Starting a new session**: read `CHANGELOG.md` and the open phase
  issues under #4 first to pick up where the project left off before
  reading through `lib/`.

### Git Workflow

- Main development branch: `main`
- Feature branches: `feature/<feature-name>`
- Bug fix branches: `bugfix/<issue-description>`
- Commit messages should be descriptive and follow conventional commits
- Commit messages are linted with [gitlint](https://jorisroovers.com/gitlint/) (config in `.gitlint`); enable the
  local hook once per clone with `git config core.hooksPath .githooks`, and CI enforces it on every PR

## Dart/Flutter Coding Conventions

### Code Style

- Follow the [Effective Dart](https://dart.dev/effective-dart) style guide
- Use `dart format` for consistent formatting (no manual style debates)
- Use `flutter analyze` / the `flutter_lints` rule set in `analysis_options.yaml`
  for linting; don't disable a lint rule without a comment explaining why
- `lowerCamelCase` for variables/functions/parameters, `UpperCamelCase` for
  types (classes, enums, extensions, typedefs), `lowercase_with_underscores`
  for file names and package/library names

### Architecture Rules

- **Layering is one-directional**: `data/` and `providers/` must never
  import anything from `presentation/theming/*`. Themes/schemes depend on
  the domain layer, never the reverse. This is what makes swapping the
  inventory scheme a real presentation-only change rather than a rewrite.
- **Add/edit forms are scheme-agnostic**, living in
  `presentation/screens/` or a shared `presentation/common/` — they are
  data entry, not game aesthetic, and every scheme reuses them.
- A new `InventoryScheme` implementation should only need to touch
  `lib/presentation/theming/<scheme_name>/` plus a registration entry in
  `scheme_registry.dart` — never the data or provider layers.

### Error Handling

- Prefer returning typed results or throwing well-described exceptions over
  silent failures; avoid `!` (null-assertion) outside of tests or cases
  where nullness has already been proven impossible a line above
- Local storage failures (drift/sqlite errors) should surface as a
  recognizable exception type from the repository layer, not leak raw
  `drift`/`sqlite3` exceptions into `providers/` or `presentation/`

### Documentation

- Add `///` doc comments to public classes/methods in `models/`, `data/`,
  and the `InventoryScheme` interface — these are the app's stable
  contracts
- Use `//` only for non-obvious *why* (a workaround, a subtle invariant),
  not to restate what the code already says

### Testing

- Unit tests for domain logic (e.g. `isExpiringSoon()`, `isLowStock()`) and
  the repository layer (against an in-memory drift database via
  `NativeDatabase.memory()`) live under `test/models/` and `test/data/`
- Widget tests (scheme rendering, form validation, scheme switching) live
  under `test/presentation/`
- Use descriptive test names: `test('<method> <scenario> <expected behavior>', ...)`
- Prefer testing behavior through the repository/provider interfaces over
  asserting on generated drift internals

## Key Patterns

### Domain model (base + category-specific attributes)

Items share a base set of fields; category-specific data (expiration for
groceries, warranty for durable goods) lives in small extension types/tables
rather than one flat model with many nullable fields, and rather than a
generic untyped key-value bag. See `lib/models/inventory_item.dart`,
`grocery_attributes.dart`, `durable_good_attributes.dart`.

```dart
enum ItemCategory { grocery, homeGood, appliance, tool }

class InventoryItem {
  final String id; // client-generated UUID (v4) — not a DB autoincrement int,
                    // so ids stay stable if cloud sync is added later
  final ItemCategory category;
  final String name;
  final int quantity;
  final String? location;
  final String? notes;
  final DateTime createdAt;
  final DateTime updatedAt;
}
```

### InventoryScheme interface (the theming plug-in point)

```dart
abstract class InventoryScheme {
  String get id;
  String get displayName;
  Widget buildHomeScreen(BuildContext context, WidgetRef ref);
  Widget buildItemSlot(BuildContext context, InventoryItem item);
  Widget buildItemDetail(BuildContext context, InventoryItem item);
}
```

Each scheme (e.g. `ZeldaInventoryScheme`) implements this against the same
underlying `InventoryItem` data — it never talks to `data/` or `providers/`
directly except by reading provider state passed in.

## AI Assistant Notes

### When Working on This Project

1. **Check current state first**: verify what exists in `lib/` before
   assuming a file/class is already there
2. **Respect the layering rule**: never add an import from
   `presentation/theming/*` into `data/` or `providers/`
3. **Test your changes**: `flutter analyze` and `flutter test` must both be
   clean before considering a change done
4. **Regenerate drift code**: after editing anything under `data/local/`,
   run `dart run build_runner build --delete-conflicting-outputs`
5. **No real game IP**: use original or clearly-licensed art/names for the
   Zelda-inspired scheme; don't bundle extracted Nintendo assets

### Common Tasks

- **Adding an item category or attribute**: extend the relevant
  category-attributes model + drift table, add a migration, update the
  repository mapping, then update each scheme's slot/detail rendering as
  needed
- **Adding a new inventory scheme**: create
  `lib/presentation/theming/<name>/`, implement `InventoryScheme`, register
  it in `scheme_registry.dart` — do not touch `data/` or `providers/`
- **Fixing a bug**: write a failing test first (unit or widget, whichever
  matches the bug), then fix
- **Adding a dependency**: use `flutter pub add <package>` (or
  `--dev <package>`) rather than hand-editing version numbers, so the
  resolver picks a compatible version

### Things to Avoid

- Don't add cloud sync now — it's an explicit Phase 4+ roadmap item; keep
  the local-only design sync-*friendly* (UUID ids, timestamps, soft
  delete) without building sync machinery
- Don't collapse the base+extension data model into one flat table with
  many nullable columns, or into a generic key-value attribute bag
- Don't let a scheme package (`presentation/theming/*`) be imported from
  `data/` or `providers/`
- Don't commit generated `*.g.dart` files (see `.gitignore`) unless the
  project's CI/build setup has explicitly changed to require it
- Don't ignore `flutter analyze` warnings or commit unformatted code
